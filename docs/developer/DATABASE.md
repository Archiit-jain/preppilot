# Database

Two schemas that mirror each other: SQLite on the device, Postgres on Supabase.
The device is the source of truth (PRD §6); the server is the copy that survives
a lost phone and follows a student to a second device.

## Tables

| Table            | Synced      | Notes                                               |
| ---------------- | ----------- | --------------------------------------------------- |
| `subjects`       | ✅          |                                                     |
| `chapters`       | ✅          | Cascades from its subject                           |
| `topics`         | ✅          | Carries a second timestamp for completion           |
| `study_sessions` | ✅          | Deliberately **no** foreign keys                    |
| `reminders`      | ✅          | `notification_id` stays local                       |
| `preferences`    | ❌          | Device-local settings, including the sync watermark |
| `profiles`       | server only | Created by a trigger on `auth.users`                |

## Columns every synced table carries

| Column                     | Purpose                                  |
| -------------------------- | ---------------------------------------- |
| `id`                       | Client-generated UUIDv7                  |
| `user_id`                  | Denormalised onto every table            |
| `created_at`, `updated_at` | Epoch ms locally, `timestamptz` remotely |
| `deleted_at`               | Tombstone                                |
| `sync_status`              | `pending` / `synced` — **local only**    |

### Why the ids are generated on the device

A row created with no network must have its final identifier immediately. If the
server assigned ids, an offline creation would hold a temporary one, and
reconciling that later is exactly how the same record ends up stored twice —
which PRD §22 forbids.

UUIDv7 rather than v4 because its leading 48 bits are a millisecond timestamp, so
ids sort by creation time and index writes stay local rather than scattering
across the B-tree.

### Why deletes are tombstones

A hard delete cannot be synchronised. The next pull from a device that has not
seen the removal cannot distinguish "deleted elsewhere" from "not yet sent", so
it re-uploads the row and the deletion is undone.

`deleted_at` makes the deletion a fact that travels. Every read filters on it;
nothing in the app issues a `DELETE`, and the server grants no delete privilege
so nothing can.

### Why `topics` has two timestamps

`updated_at` covers the row. `completed_changed_at` covers only the tick.

Without the second one, renaming a topic on a phone and ticking it on a tablet
are indistinguishable — both are "the row changed at time T" — so one silently
reverts the other. Since un-ticking finished work is the outcome a student would
least forgive, completion resolves on its own timestamp.

### Why `study_sessions` has no foreign keys

Deleting a subject must not shrink "total time studied using PrepPilot" (PRD
§12). The student really did spend that time.

The subject, chapter and topic ids are plain columns used for filtering, and the
names are **snapshots** taken when the session was recorded — so history stays
readable after a rename, and survives a delete.

## Migrations

Local (`apps/mobile/drizzle/`) are generated by drizzle-kit from
`src/db/schema.ts` and applied by `migrate()` when the database opens. Never edit
a generated file; change the schema and regenerate.

```bash
pnpm --filter @preppilot/mobile exec drizzle-kit generate
```

Server (`supabase/migrations/`) are hand-written and applied with the CLI.

```bash
supabase db push          # against a linked project
supabase db reset         # against the local stack, for testing
```

### Notes, conversations and the Quiz deck (September 2026)

Migration `20260924000001_notes_chats_quizzes.sql` adds four synchronised tables,
with the same conventions as the rest (client UUIDv7 ids, tombstones, server-set
`updated_at`, forced RLS, no delete policy):

| Table           | Holds                                                                                            |
| --------------- | ------------------------------------------------------------------------------------------------ |
| `notes`         | Any number of notes per topic or sub-topic, with their source (`manual`, `summary`, `assistant`) |
| `chat_threads`  | Saved conversations with the assistant                                                           |
| `chat_messages` | Their messages; `proposal` as JSON; `has_image` (the picture itself stays on the device)         |
| `quiz_attempts` | Finished quizzes: settings, questions and answers as JSON, score                                 |

`topics.note` and `subtopics.note` remain for older app versions but are no
longer written. `NoteRepository.adoptLegacy` copies any note found there into
`notes` under the topic's own id, so two devices adopting the same note write
one row, and a deleted adopted note is not brought back.

The live project's migration history was empty (it was set up by pasting SQL),
so the four earlier migrations were marked applied with
`supabase migration repair --status applied <versions>` before `supabase db
push` applied the new one. A plain `db push` would have re-run them and stopped
on existing policies.

`20260925000001_chat_follow_up.sql` adds `chat_threads.follow_up`, the summary a
follow-up chat carries. Older app versions ignore the extra column when they
sync: Drizzle drops keys that are not in the local schema.

`20261002000001_theme_packs_bucket.sql` creates the public, read-only `themes`
Storage bucket that holds downloadable themes (THEMES.md). It creates no table
and no write policy.

`supabase/apply-all-migrations.sql` holds all seven migrations in order, written
to be safe to run more than once, for pasting into the Supabase SQL Editor where
the CLI is not available. The live project was set up that way (21 September
2026). When a migration is added, add it to that file too.

### Grants are not optional

Enabling RLS is not enough. RLS filters rows only **after** the privilege check
passes, so a table with policies and no `GRANT` rejects every request outright
rather than returning an empty set.

Both migrations originally had this bug. It was invisible until the SQL was run
against a real Postgres. Any new table needs:

```sql
grant select, insert, update on public.<table> to authenticated;
```

Delete is deliberately withheld everywhere.

## Testing against a real database

Repository tests run the **generated migrations** against in-memory SQLite via
`better-sqlite3`. Both it and `expo-sqlite` are synchronous Drizzle cores, so the
tests execute the SQL the app ships — constraints, cascades, indexes and ordering
included — rather than a mock that agrees with whatever the code does.

The harness applies every migration in order. Adding one requires no change to it.
